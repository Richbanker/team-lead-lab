# Как оценивать задержку сводки

Плановое время берём из [расписания workflow](../.github/workflows/team-pulse.yml) в часовом поясе Москвы. К этому времени отчёт должен появиться в [журнале #1](https://github.com/Richbanker/team-lead-lab/issues/1). Для пилота предлагаем начинать разбор, если через 30 минут отчёта всё ещё нет. Если Actions уже показывает ошибку, откройте лог сразу.

| Окно | Ожидаемая публикация, МСК | Допустимая задержка | Действие при превышении |
| --- | --- | --- | --- |
| Утро | 09:00 | 30 минут | В 09:30 проверить запуск и журнал перед разбором утренних задач. |
| Обед | 13:00 | 30 минут | В 13:30 проверить запуск и журнал перед проверкой статусов. |
| Вечер | 18:00 | 30 минут | В 18:30 проверить запуск и журнал перед подведением итогов дня. |

Для всех трёх окон предлагаем один порог. В проверенных примерах от создания запуска до публикации проходило **7–9 секунд**, а от планового времени до создания запуска — **от 5:57:04 до 10:44:49**. Тайм-аут задания составляет 5 минут. Полчаса оставляют запас на запуск и выполнение и позволяют заметить задержку задолго до следующего окна. Это порог реакции для тимлида. Надёжность расписания по такой выборке оценить нельзя.

## Как повторить расчёт

1. В [истории Actions](https://github.com/Richbanker/team-lead-lab/actions/workflows/team-pulse.yml) откройте запуск с событием `schedule`. В шаге **Опубликовать сводку** проверьте `REPORT_SCHEDULE`. В **Summary** откройте **Открыть опубликованную сводку** и сверьте ссылку с URL из лога. Ручная сводка учитывается отдельно.
2. Зафиксируйте плановое время окна, `created_at` запуска и `created_at` комментария. Полная задержка равна времени публикации минус плановое время. Для повторной публикации по тому же URL `created_at` остаётся временем первой публикации, а последнее изменение видно в `updated_at`.
3. Для [утренней сводки 22 ноября](https://github.com/Richbanker/team-lead-lab/actions/runs/45030343301) выполните в PowerShell:

```powershell
$api = 'https://api.github.com/repos/Richbanker/team-lead-lab'
$run = Invoke-RestMethod "$api/actions/runs/45030343301"
$comment = Invoke-RestMethod "$api/issues/comments/7080209700"
$expected = [datetimeoffset]'2026-11-22T09:00:00+03:00'
$runCreated = [datetimeoffset]$run.created_at
$published = [datetimeoffset]$comment.created_at
$runCreated - $expected       # 07:59:26 до создания запуска
$published - $runCreated    # 00:00:08 от создания запуска до публикации
$published - $expected      # 07:59:34 общая задержка
```

## Где искать причину

| Наблюдение | Что проверить |
| --- | --- |
| К контрольному времени подходящего запуска нет | Убедитесь, что workflow включён и расписание есть в `main`. Проверьте историю повторно и запишите, когда появилась запись о запуске. |
| Запуск создан поздно или долго ждёт выполнения | Сравните плановое время с `created_at` запуска. Если запись появилась вовремя, проверьте статус очереди и время начала задания **report**. |
| Запуск завершился ошибкой | Откройте первый шаг со статусом ошибки. Ошибка до **Опубликовать сводку** указывает на сбой выполнения. Ошибка в этом шаге требует проверки сообщения скрипта и ответа API. |
| Запуск успешен, а сводки нет или она появилась поздно | Проверьте URL из **Summary**, доступность комментария, дату и название окна. Если запуск был вовремя, а правильный комментарий создан после порога, разбирайте интервал от запуска до публикации. Если ссылка расходится с журналом, зафиксируйте, где именно оборвалась проверка. |

Если сводка нужна до завершения разбора, тимлид может запросить её из **Actions → Сводка по задачам → Run workflow**. Для разбора сохраните ссылки на запуск и комментарий, а также измеренные интервалы.
